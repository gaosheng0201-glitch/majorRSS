> 现在不做——先作为设计意图沉淀，择机分步实现。相关：`llm/investigator.py`、
> `backend/api/settings.py`（/investigate 端点）、`docs/vision_and_blueprint.md`（fact_level / 线索生命周期）。

## 1. 原始设计意图（作者亲述）

一条小道消息（例：某模型要发布、某手机样式被提前公布）传到你手上时，**往往已经被转发、转译过很多次**、可能失真。这个功能要做两件事：

1. **溯源**：把消息追回**最初的源头**，还原它最开始到底说了什么。
2. **反幻觉**：不信任单个大模型的"自洽幻觉"，用**两个模型交叉验证**同一件事的源头。

一句话：**把失真的小道消息追到一手源头 + 用双模型交叉验证还原真相。**

## 2. 当前实现（`llm/investigator.py`）与差距

现状：两条流水线并列，用户在"竞技场"里肉眼对比。
- Pipeline A `run_native_grounding`：Gemini 原生 Google Search grounding（黑盒联网核查）。
- Pipeline B `run_major_funnel`：DDG 搜 → LLM 挑 1-2 个"权威" URL → AgenticScraper 深抓 → LLM 判定。

**三个不成熟点：**

### ① "权威" ≠ "源头"
溯源要的是**最早的一手源头**（官方博客 / 爆料者原帖 / 原始文件），不是"权威页面"——权威媒体往往就是转述方。当前漏斗只挑"权威 URL"，**没有沿时间线和引用链上溯**，所以名为溯源、实为"找权威"。

### ② "两个模型"不是真正的独立交叉验证
- 两条流水线**证据不同、方法不同**（A 黑盒联网 vs B 透明抓取），比的是苹果和橘子，不是干净的交叉验证。
- **同厂同族模型共享偏见与幻觉**——"两个模型"只有来自**不同家族**（如 Gemini + 本地/OpenAI 模型）时才真正抗幻觉。同模型跑两遍盲区一样。
- 缺**结构化的"一致/分歧"判定**：真正的反幻觉是——两个独立模型对**同一份抽取出的源头证据**各自独立下判断，**一致才算证实、分歧就明确标"存在争议"并摆出两边理由**（而非合并成一个自洽答案）。

### ③ 没有"还原真相"（失真对照）
核心价值是展示"你听到的版本 vs 源头原话"的**失真过程**（翻译错误、夸大、加戏）。当前只输出一个判定，没把这个 drift 显出来——而这恰是最有价值的部分。

## 3. 成熟设计方向

```text
你听到的小道消息（可能已失真）
  ↓
① 收集提及集：多路搜索（DDG + Google News + 本地雷达已有线索）
   每条提取：URL / 发布时间 / 发布方 / 是否引用更早的源
  ↓
② 溯源（真·溯源）：按时间排序 + 顺引用链上溯
   → 定位最早的一手源头；区分「原始」vs「转发/转译」
   → 产出溯源链：源头 → 转述A → 转译B → … → 你
  ↓
③ 从源头（+ 顶部一手佐证）抓一次证据（只抓一次，两模型看同一份）
  ↓
④ 双模型独立交叉验证（不同家族的模型）
   模型1、模型2 各自独立回答：源头到底说了什么？你听到的版本差在哪？判定？
   → 一致 = 证实（高置信）；分歧 = 明确标「存在争议」，两边理由都摆出
  ↓
⑤ 输出：溯源链 + 「源头原话 vs 你听到的版本」失真对照 + 双模型判定（含分歧）
   置信度 = 是否追到一手源 × 双模型是否一致 × 佐证数
```

**复用雷达已有概念（不要另起孤岛）**：`LEAD→CORROBORATED→CONFIRMED`、
`fact_level: observed/verified/disputed`、一手来源追猎、佐证数。Investigator 本质是
**"雷达被动做的事的一次性深度版"**——要追的小道消息很多时候雷达里已是一条 StoryThread
（已按时间排源、已追过一手），Investigator 可直接从该线索起步，而非从零搜。

## 4. 前置条件（已完成）

- **Provider 抽象已打通**（2026-07-21）：`llm/investigator.py` 已迁到 `get_provider().generate()`，
  不再 Gemini-only。这是 ④「双模型需来自不同家族」的前置——现在可配置两个不同后端
  （如 Gemini + 本地 Ollama）分别独立判定。原生 grounding（A）保留为 Gemini 专属能力并加守卫。

## 4.5 作者裁决（2026-07-29）：砍掉竞技场与双模型，只留溯源

> **"竞技场功能不要 A/B 测试了，伪需求。只保留一个功能：复用我应用的搜索管线，去针对性查用户想了解的小道消息是否属实、或者源头是什么。"**

**砍掉**：
- ❌ **竞技场 UI**（两条流水线并列、用户肉眼对比）——伪需求。用户要的是答案，不是评委席。
- ❌ **双模型交叉验证**（原 ④）——本文档 §2② 早已指出现状那两条流水线"证据不同、方法不同，比的是苹果和橘子"，不是干净的交叉验证；作者现在直接裁掉这个方向，不再补做"真正的双模型"。

**保留（唯一功能）**：**输入一条小道消息 → 复用应用自己的搜索管线去查 → 给出源头与佐证结构。**

这个裁决把重设计**大幅简化**，而且和主管线的演进对齐——"复用搜索管线"现在比当初写这份文档时值钱得多：
- **多语言分路**（语言三原则②，2026-07-29 落地）：小道消息常先在非英语圈流传，按信源语言分版本查才追得到源头
- **来源分层**（`source_tier`）：PRIMARY/一手直接就是"源头"的判据
- **真实出版方计数 + 去同源**（P0.4/⑤）：能识破"十家转载同一篇通稿"的伪佐证——**溯源最需要的正是这个**
- **抽取式**（愿景 184 行）：呈现源头原话而非 AI 改写，正合「真相与溯源」

**边界不变**：不承诺"事实核查"权威结论；承诺"追到源头 + 展示佐证/分歧结构，**判断权在用户**"。
