# 雷达质量与成本路线图（抓取 → 聚类 → 整合 → 反馈）

>
> 来源：2026-07-23 作者与 Claude 的设计讨论（"grok 每轮抓不完""简报基于什么""引用/重复来源标签""打分优化向量""费用"）。
> 相关：`docs/vision_and_blueprint.md`（增量优先、反馈闭环盲区#1、when:7d、结构性省钱）、
> `docs/semantic_layer_audit.md`（语义层收口，已做）、`docs/investigator_redesign.md`。

## 0. 排序的第一原则：信任链自下而上，反馈闭环放最后

```text
抓取(intake) → 聚类(cluster) → 整合/简报(synthesis) → 反馈(feedback)
     └────────── 下游的正确性依赖上游 ──────────┘
```

**关键约束（作者定）：向量/评分反馈必须最后做。** 反馈闭环会把"当前基准"固化进画像向量和来源权重——如果此时抓取还在拉宽窗口重复、聚类还在误合并、简报还基于错的管线，那么**在脏基准上评分 = 把错误当信号学进去，越训越偏**。所以先把上游修可信，再上反馈。

聚类那一层（去均值 + LLM 事件仲裁 + 跨语言）已在 2026-07-23 收口（见 semantic_layer_audit）。以下是剩余项的排序。

## P0 — 立即（小改、提正确性、直接省钱、无依赖）

两项都是低风险小改，且直接砍成本，先做。

### P0.1 Google News 查询加 `when:Nd` 源头日期限定 ✅（2026-07-23 已做，用 max_days）
- **问题**：查询是 `search?q=grok`，无日期限定；只有抓回来后的 `max_days=7` 年龄门（抓后过滤）。愿景 line 87 明确要"`when:7d`，源头拦截优于抓后过滤"——设计了没做。
- **后果**：每轮拉一个宽窗口，URL 去重挡住了重复入库，但白抓、白解析、（相关项）白 embed。热点话题尤其烧。
- **改**：gnews 路由 query 拼 `when:7d`（快话题）/按规划器的回填窗口天数；其他可日期化的源同理。`services/source_resolver.py`。
- **成本影响**：直接减少重复抓取 + 重复 embed。

### P0.2 融合摘要标签：`摘要引用来源` / `重复来源`
- **问题**：现在写"本次融合的所有原始 URL（**含被过滤的噪音**）"——但未引用的大多是**同一事件的其他媒体报道（重复/佐证），不是噪音**。措辞误导。
- **改**：`services/processor_service.py` 摘要模板 → "摘要引用来源" + "重复/佐证来源"；真被相关性门过滤掉的单列"已过滤"（如有）。
- **成本影响**：无，纯 UX 正确性。

## P1 — 摄入可信 + 成本闸门（反馈的前置）

### P1.1 融合按重要度/共振门控（结构性省钱）
- **问题**：fusion 似乎每批未处理文章都做 LLM 融合摘要。愿景原则是"大多数内容从生到死不碰生成模型"，热点话题下这是主要 token 黑洞之一。
- **改**：只对**值得的线索**做 LLM 融合——高重要度 / 已共振 / 高关注目标；低价值线索停在 embedding 层（雷达仍显示线索，只是不烧生成模型写摘要）。`services/processor_service.py` + 线索重要度信号。
- **成本影响**：大。把生成模型消耗从"每批"降到"值得的少数"。

### P1.2 成本可视化 + 预算护栏收口
- embedding 记账已补（2026-07-23）、计费按模型分算已做。剩：把**每目标成本**在 UI 显示（愿景 line 151 "预算从每日 token 上限进化为每目标每日成本，UI 可见哪个目标在烧钱"），并让预算刹车覆盖 embedding + 仲裁。
- 本地嵌入选项已做 UI（指向 Ollama 免费）——文档化"想省钱就切本地嵌入"。

## P2 — 单一"发生了什么"管线（架构债，反馈的前置）

### P2.1 每日简报改为基于线索（StoryThread），而非平行的 IntelReport 融合
- **问题**：现在库里 **StoryThread（雷达用）+ IntelReport（简报用）是两条平行的"发生了什么"管线**。雷达走"embed→聚类→线索"，简报走老的"文章→LLM 融合→IntelReport"。愿景 line 73-74 本意是**知识状态（线索）同时驱动线索合成 + 每日简报**。
- **后果**：两套重叠管线——费 token、可能不一致、且**反馈没有唯一可信的基准可训**。
- **改**：简报从"最近 N 天的线索及其增量"合成；IntelReport 要么淘汰、要么退化为"线索的一次合成产物"（与 P1.1 的门控融合合并成一件事）。这是本路线图里最大的一块。
- **为什么在反馈之前**：反馈要标注的对象是"线索"。若线索和简报是两套数据，反馈训练的基准就不唯一、不可信。

## P3 — 反馈闭环（最后做，愿景盲区 #1）

### P3.1 线索/告警打分 → 负反馈调权
- **设计已存在**（愿景盲区 #1，→R5，未实现）：每条线索/告警可标"值得 / 不值得 / 别再报(mute)"，负反馈调**画像向量 + 来源权重 + 线索静音**。
- **就是作者说的"打分 + 同步优化向量"。** 好评上权喜欢的方向、差评下权、mute 静音同类。顺带解决热点噪音（标"grok 赛季模拟"不值得 → 同类降权）。
- **必须最后做（作者定）**：它把当前基准固化进画像向量。**只有当 P0（抓取不再拉宽窗口）+ P1（融合只对值得的做）+ P2（线索是唯一可信基准）都到位后，反馈学到的才是真信号；否则在脏基准上评分只会进一步污染。**
- 落地：`RadarAlert`/`StoryThread` 加反馈字段 + 端点；画像向量 = 正反馈样本的加权中心，相关性门叠加个性化偏移；来源权重进 source_health 或新表；mute 用线索指纹。

## 一页纸总结

| 阶段 | 做什么 | 为什么这个顺序 | 成本影响 |
|---|---|---|---|
| **P0.1** | gnews `when:7d` 源头日期限定 | 无依赖、直接省钱 | ↓↓ |
| **P0.2** | 标签"引用来源/重复来源" | 无依赖、纯正确性 | — |
| **P1.1** | 融合按重要度门控 | 摄入省钱、反馈前置 | ↓↓↓ |
| **P1.2** | 每目标成本可视化 + 本地嵌入文档化 | 成本护栏收口 | ↓ |
| **P2.1** | 简报改基于线索、统一管线 | 给反馈一个唯一可信基准 | ↓ + 消除债 |
| **P3.1** | 打分反馈 → 调画像向量/来源权重/静音 | **必须在上游可信之后**，否则污染基准 | — |

**一句话**：先让"抓什么、怎么聚、怎么整合"变可信且省钱（P0–P2），再让用户的评分去精调这个可信基准（P3）。反过来做，等于在歪的尺子上刻度。

# 附：P1.1 + P2.1 合并方案细化（待作者确认，未实现）

> P1.1（融合门控省钱）与 P2.1（简报基于线索、统一管线）**是同一件事的两面**，应合并做。核心：**融合从"作用于文章批、每批都烧"改为"作用于线索、只对值得的烧"，摘要落在线索上，简报和大屏都读线索。** 一举同时省钱 + 消架构债 + 给反馈一个唯一可信基准。

## A. 现状（要改掉的）

两条平行的"发生了什么"管线：
- **线索管线**：`embed → 聚类 → StoryThread`（标题 + 来源 + 生命周期 + 共振）。**无 LLM 摘要**（只有 R5 告警引擎对告警级线索合成了带引用的摘要）。
- **融合管线**：`未处理文章批 → LLM 融合（每批都烧）→ IntelReport（摘要）→ 每日简报 + RSS 导出`。

问题：① 融合每批都烧 = 热点话题最大 token 黑洞；② IntelReport 是与线索平行的"发生了什么"存储，二者可能不一致；③ 简报基于 IntelReport 而非线索；④ 反馈没有唯一基准可训。

## B. 目标设计

1. **融合作用于线索**：融合单元 = 一条 StoryThread 的成员文章（一条线索 = 一个事件）。不再按"未处理文章批"随意成批。
2. **便宜门控（唯一要拍板的设计点）**：只对满足以下**任一**的线索烧 LLM 融合——
   - `is_resonant`（短时跨多独立源汇聚）
   - `distinct_source_count ≥ FUSION_MIN_SOURCES`（默认 3，即 CORROBORATED+）
   - `lifecycle == CONFIRMED`（有一手来源，**即使单源也过门**——防漏独家一手猛料）
   - `tracker.is_high_attention`（用户标了高关注 → 一律融合）
   - 未过门的线索：**不烧 LLM**，雷达照常显示标题 + 来源 + 生命周期。
   - 这些阈值做成**可调常量**（`FUSION_MIN_SOURCES` 等）。
3. **摘要落在线索上**：给 `StoryThread` 加 `summary` 字段（LLM 合成的事件摘要 + 引用来源 + 佐证来源，沿用 P0.2 的诚实标签）。**单一数据源**，不再另建 IntelReport。
   - 过渡可选：IntelReport 表保留但语义变为"线索摘要快照"（加 `thread_id` 外键、1:1 绑线索），逐步淘汰；渐进迁移更稳。
4. **复用 R5 已有合成**：`services/alert_engine.py` 已实现"线索合成带引用溯源、无 model 降级为纯引用"。**线索摘要直接复用这套**，融合本质 = 给过门线索调用它，不重造轮子。
5. **增量再合成，受控频率**：线索有真实增量（新独立源、生命周期升级 LEAD→CORROBORATED→CONFIRMED、跨过门控阈值）时才重新合成摘要；普通新成员只更新来源列表、不重烧。
6. **简报基于线索**：`generate_daily_briefing` 从"最近 N 天有摘要 / 有增量的线索"合成，替代读 IntelReport。
7. **大屏 / RSS 导出读线索**：`export_rss` 与情报大屏都读 `thread.summary`，淘汰 IntelReport 直出。
8. **手动摘要兜底**：雷达每条线索加"生成摘要"按钮——便宜门漏掉、但用户觉得值的（如真·独家单源），一键补摘要。这是门控漏报的安全网。

## C. 成本与效果

- **省钱**：融合从"每批 10 篇都烧"降到"过门线索"（估计约 20%）——砍掉大部分生成开销。embedding + 仲裁开销不变（那是聚类层，已在预算记账内）。
- **效果不降反升**：重要事件（共振/多源/确证/高关注）照常有摘要；琐碎单源事件失去一段本就多余的 AI 段落，但保留标题+来源——符合愿证"默认安静，打扰需要证明自己值得"。**雷达不丢任何事件**，只是把 AI 归纳留给值得的。
- **唯一真风险**：门控漏掉真·独家单源猛料 → 三重缓解：CONFIRMED 单源过门 + 高关注一律过 + 手动摘要按钮。

## D. 实施步骤（建议顺序）

1. **Step A** — 融合输入从"未处理文章批"改为"线索成员"（`services/processor_service.py`）。
2. **Step B** — 加便宜门控（只对过门线索融合），阈值常量化。
3. **Step C** — 线索摘要落 `StoryThread.summary`（迁移：或先 IntelReport 绑 `thread_id`）；复用 alert_engine 的合成。
4. **Step D** — `generate_daily_briefing` 改读线索。
5. **Step E** — 大屏 / `export_rss` 改读线索；雷达加"生成摘要"按钮。
6. **验证** — 门控命中率（多少线索过门）、token 前后对比、简报内容与线索一致、漏报独家单源的手动兜底可用。

## E. 迁移与风险

- **数据**：IntelReport 现有 15 条 → 迁移期作为"线索摘要快照"（绑 thread_id）或清空重生成（派生数据，可重建）。
- **反馈前置**：P2.1 完成后，**线索成为唯一"发生了什么"基准**，P3 反馈才有干净的标注对象——这是把 P3 排最后的技术原因之一。
- **不做的**：不在本阶段引入"重要度 LLM 预判"（那会把省下的钱又烧回去）；门控只用聚类层已有的便宜信号。

## F. 待作者拍板的点

2. 线索摘要落 `StoryThread.summary`（推荐）还是 IntelReport 绑 thread_id（渐进）。
3. 是否本阶段就淘汰 IntelReport / RSS 直出，还是留过渡。
4. 手动"生成摘要"按钮是否本阶段做（建议做，是门控的安全网）。
