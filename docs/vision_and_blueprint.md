## 1. 愿景（作者亲述，2026-07-05）

1. **源起**：想知道一手消息，但不想在信息大海里浪费时间；噪音消耗心神。相信这是普遍需求——有人追行业，有人看时政，有人跟踪自己罕见病的进展。**服务所有人，但运行在各自的终端上**：降低成本、保证隐私和 cookie 安全。不具备使用条件的人，可以通过作者的**公开网站**看到去噪后的信息。
2. **主动性**：默认静默运行，不频繁跳通知——否则和社交媒体的注意力经济没有区别。但两种情况必须主动提示防止错过：重量级消息；用户自己标记的高关注目标。另外，**当媒体和社交平台都在讨论用户关注的事情时，这本身就是重要性信号**。
3. **模型**：BYOK（用户自带 Key）为主；兼容本地模型最好，照顾更注重隐私的用户。
4. **作者本人的用例**（第一批验收标准）：
   - 同时关注多个领域的前沿消息
   - 痛恨毒新闻和营销号的捏造与夸大——**需要真实情况或源头**
   - 需要**低成本方式**监测 API 文档 / changelog 是否更新（厂商不发邮件通知）

**同日第二次补充陈述：**

5. **共享 token（产品口号）**：OnlyFourBot 是要做的。"如果我在消耗 token 获取某个别人也想了解的信息，应该共享结果，而不是每个人为同样的信息买单、浪费算力。"本项目同时是作者自媒体内容的一部分（配合节目推出、免费使用），已有专门域名承载这些信息。
6. **登录与追溯**：网站分享需要账号体系——追溯用户分享的信源、垃圾信息责任；账号与作者其他应用打通（像 Google 一个账号登录所有应用），可复用同一 Supabase 实例以节约成本。
7. **时效性**：社交媒体的信息往往比官方和媒体快好几天（例：新 iPhone 在代工厂被曝光，媒体报道时已发酵多日）。作者做自媒体需要足够时效的**线报**。
8. **合规**：分享出去的内容必须做隐私过滤（地址、身份识别号等），避免被用于不合规用途；登录态获得的信息不能在网站分享（沿用）；摘要还是原文的问题交由工程判断 → 结论见 3.2「发布合规策略」。
9. **分发与更新**：应用需要登录（见 #6）并支持**在线更新**；必须防止更新通道或安装包被人植入木马 → 结论见 3.2「分发与更新安全」。

## 2. 产品原则（从愿景推导，用于裁决一切设计争议）

| 原则 | 含义 | 反面 |
|---|---|---|
| **注意力保护** | KPI 是为用户省下的时间，不是停留时长；默认安静，打扰需要证明自己值得 | 社交媒体的注意力经济 |
| **增量优先** | 噪音的定义 = 与用户已知状态没有增量的信息；输出是"发生了什么变化"，不是"有多少新内容" | 无限下拉的 feed |
| **真相与溯源** | 每条合成结论可追溯到源头链接；多源佐证数可见；优先呈现一手来源（官方公告 > 转述媒体 > 社交讨论） | 不可考证的"AI 总结" |
| **本地与隐私** | 抓取、cookie、知识状态全在用户终端；模型 BYOK 或本地 | 云端代抓、上传凭证 |
| **信息是主角** | 屏幕上最大、最先出现的应是"发生了什么"（情报/线索本身）；关于情报的元信息（统计数字、徽章、状态）永远次要、安静、可折叠 | 一屏数字卡片，真实信息被挤到下面或缺席（分析仪表盘反模式） |

**信息设计纪律（2026-07-06 补，蓝图原缺口——只有"注意力保护"原则没有落地规范，导致 UI 越加越挤）：**
- **内容优先**：每个界面第一眼看到的必须是信息本身，不是关于信息的统计。stats/KPI 是一行安静的文字，不是和内容抢视觉权重的卡片网格。
- **一个主界面**：日用界面只有一个（雷达/线索视图就是"仪表盘"，R6 的"换心脏"是替换不是新增）。不要让两个界面展示相似内容。
- **像素预算**：加任何元素前先问"它配得上这块屏幕吗"。默认答案是否。宁可留白，不可堆砌。徽章、边框、卡片是稀缺资源。
- **渐进式展开**：次要信息（诊断、统计、来源列表、账号状态）默认折叠/次级页面，按需展开，不在主视线里。
- **安静**：默认低对比、少边框、多留白，让眼睛能休息。打扰（高对比色、徽章）必须证明自己值得。
- **验收**：任何 UI 改动后，"3 分钟摄入一天"的标准要求主视线里是信息不是仪表盘 chrome。加法若增加了首屏元信息密度，就是做错了方向。
| **时效与置信分离** | 快（线报）和真（证实）是两个维度，分开标注而不是互相牺牲：LEAD → 多源佐证 → 一手证实 | 为了快而传谣，或为了稳而迟到 |

## 3. 目标架构

### 3.1 总览

```text
用户 → Watch Target（关注目标，产品单位）
         │  建目标时 LLM 规划一次 → Source Portfolio（选源组合+节奏+预算，JSON）
         ▼
获取运行时（确定性执行，零 token）
  ├─ HTTP 抓取（条件 GET：ETag/Last-Modified，轮询近零成本）
  ├─ 常驻浏览器池（每 auth profile 一个持久上下文；per-domain 限速+退避）
  ├─ 页面 diff（内容哈希 → 干净结构化 diff，changelog 模式）
  └─ 正文提取（readability 级别，干净文本=更少 token）
         ▼
统一 Item 主干（一切获取方法产出统一 SourceItem，单管线 ingest）
         ▼
语义层（embedding，本地或 API，近零成本）
  ├─ 相关性门：与目标画像的向量距离 + 关键词规则 → 不相关不入库
  ├─ 去重：与已有线索相似度 → 旧闻归并，不打扰
  └─ 聚类：新内容归入 / 新建事件线索（Story Thread）
         ▼
知识状态（每目标一份：线索集合 + 各线索当前已知事实）
         ▼
生成模型（只做四件事，全部低频）
  ├─ 建目标时的 portfolio 规划
  ├─ 线索出现真实增量时的合成（带引用溯源）
  ├─ 每日简报
  └─ 共振告警的说明文案
         ▼
输出层
  ├─ 桌面 UI：目标 → 线索 → 增量视图（默认安静的仪表盘）
  ├─ 告警引擎：重量级 / 高关注 / 跨源共振 → 系统通知
  └─ 发布层（可选）：digest → 静态站点 / generated RSS → 作者公开网站
```

### 3.2 关键机制

**Watch Target 与知识状态**
- Target = { 名称, 实体画像(别名/相关人/相关机构), portfolio, 优先级(普通/高关注), 预算 }
- **时间语义（作者确认的担忧：建目标不能把十年旧闻拉进来）**：雷达与检索分离。雷达语义=Watch Target 默认"从现在起报新"，建目标时仅做**预热回填窗**（大小由规划器按话题节奏建议：快话题 7 天/慢话题 90 天，用户可覆盖——原手动周期设置保留为覆盖项）；窗口由入库年龄门执行（max_days 机制延续），搜索源在 query 层限定日期（如 Google News `when:7d`，源头拦截优于抓后过滤）。检索语义=可选的一次性**背景调查**（Investigator 的归宿），结果标注"背景"进线索资料，永不冒充新进展、不触发告警。细节：`published_at`（发布时间，用于年龄门）与 `first_seen`（雷达首见，用于增量逻辑）分离——无日期来源按首见保守处理；旧文突然回热按发布时间会被拦，但"回热"本身是共振信号，此时以线索背景引用身份进入而非"新消息"。
- **数据引擎策略（作者确认）**：SQLite 永远是默认（零配置=节目推广场景不可妥协），Postgres 是高级选项。纪律：核心路径只用两引擎公共子集，引擎专属特性不进主干；R3 向量层加抽象，默认实现用引擎无关的暴力余弦（个人雷达量级 numpy 毫秒级），pgvector/sqlite-vec 留作可选加速。注：作者感受的"SQLite 性能弱"大部分源于已修复的工艺问题（无 busy_timeout/会话泄漏/NullPool churn），真实瓶颈以测量为准。共享层的 Supabase 是服务端世界，与本地引擎选择无关。
- **语言三原则**（推演结论，2026-07-05）：① 任何语言的输入都归一化为**语言无关实体画像**（含多语言别名），输入语言只决定叙述语言、不决定搜索范围——话题的信源地理分布是话题属性（例：Apple Siri = EN 一手 + ja 供应链 + zh 爆料）；② 搜索 query 按**信源的语言**生成（Google News hl/gl 分路），不按用户语言；③ 输入语言可作为关注角度的弱信号做加法个性化（ja 用户加"Siri 日本語対応"角度），永不做减法。跨语言同线索的时序自动呈现"源头→转述链"（最早≈最接近一手）；共享层的线索状态语言无关，全球同话题只烧一次理解，叙述按语言便宜生成/缓存。
- Thread = 一个事件/议题的聚类，携带状态：已知事实、来源列表、佐证数、最后更新时间
- 新 item 的命运只有三种：不相关（丢弃，trace 记录原因）→ 旧闻（归并线索，静默）→ 增量（更新线索，视重要性决定是否告警）

**线索生命周期（愿景 #7 时效性的解法：快和真分离标注，互不牺牲）**
```text
LEAD（线报）        单源、来自社交/论坛、未证实 —— 速度优先，明确标注"未证实线报"
  ↓ 更多独立来源加入
CORROBORATED（多源） N 个独立来源佐证 —— 佐证数可见
  ↓ 官方公告/一手来源出现
CONFIRMED（证实）    一手来源在线索中置顶
```
- 社交源天然领先媒体数天——LEAD 状态让线报第一时间可见而不冒充新闻
- 高关注目标可订阅 LEAD 级提示（自媒体抢时效场景）；普通目标默认 CORROBORATED 起告警
- 共振检测即 LEAD → CORROBORATED 的跃迁速度，跃迁越快信号越强

**共振检测（愿景 #2 的信号）**
- 线索速度 = 单位时间内加入同一线索的**独立来源数**（媒体域名、社交平台分开计数）
- 检测本身零 token（纯计数）；超过阈值才让 LLM 写一段告警说明
- 现有 TrendAlert（实体×源计数）是雏形，升级为线索级

**告警引擎（默认安静）**
- 触发条件（或）：线索重要性 ≥ 阈值；目标被标记高关注且有增量；共振速度超阈
- 通道：Tauri 系统通知；每日简报兜底汇总所有未告警增量
- 原则：每条告警在 UI 里可回答"为什么打扰我"（触发原因可见）

**溯源与求真（愿景 #4）**
- 合成必须带引用：每条结论列出支撑来源链接
- 佐证数可见："3 个独立来源" vs "仅 1 个营销号"一目了然
- 一手来源追猎：新闻转述中提取被引用的原始出处（官方博客/公告/论文/repo），线索置顶展示源头而非转述
- 不承诺"事实核查"，承诺"给你源头和佐证结构，判断权在你"

**Changelog 监测（愿景 #4，作者刚需，"低配"实现）**
- 条件 GET + 内容哈希：没变化时成本为一次 HTTP 头交换，零解析零 token
- 变化时：结构化 diff（过滤广告/导航/时间戳噪音，支持 selector 圈定区域）→ 仅真实内容变化才可选 LLM 一句话总结
- changelog 模式：识别版本号/日期条目型页面，diff 输出"新增了哪些条目"

**授权会话保护（防账号被封，2026-07-05 作者提出的盲区）**
> 心智：认证会话不是"抓取能力"，是用户借给应用的**易碎信用**——花它要像花别人的钱一样谨慎。产品的核心卖点"关注很多"与账号安全直接对冲（关注越多=账号活动越频繁=越像爬虫），因此账号保护必须是 auth 架构的一等支柱，不是限速的附属品。被封的是用户不可替代的真实账号，后果远重于普通抓取失败。
- **① 每账号预算（关键）**：限速挂在 **auth 会话**上，不是挂在目标/域名上。N 个目标共用一个平台登录 → 该平台每小时授权请求数有账号级全局上限；目标数量增长绝不线性放大账号活动量，超预算目标排队而非齐冲。
- **② 拟人化节奏**：随机抖动间隔（非整点轮询）、账号时区的夜间静默窗、请求间随机停顿、单次会话拉取量上限。宁可慢，不可规律得像机器。
- **③ 会话隔离 + 指纹稳定**：每个 auth profile 用独立且**持久**的浏览器上下文（R1 浏览器池提供），让同一账号每次看起来是同一台设备；避免指纹每次都变（现状）或多账号共用指纹。
- **④ 风控熔断器（最高优先级）**：撞到验证码/429/限制页 → 立即熔断该账号**全部**授权抓取（非仅当前目标），指数退避，UI 明确告知"你的 X 账号被限流，已暂停授权抓取 N 小时以保护账号"。绝不撞墙后下一轮接着撞。
- **⑤ 降级而非硬刚**：授权路由熔断时自动降级到匿名路由（公开 RSS/镜像/Google News），以能力换安全，账号活着。呼应原始"降级升维"设计，把账号安全加进降级触发条件。
- **⑥ 知情同意 + 默认保守**：授权平台时明确提示"用真实账号访问，已限速保护，但平台可能视为自动化，存在风险"；默认最保守节奏，激进是用户主动开启的选项。
- **诚实边界**：无法 100% 保证不被封（风控是黑盒且多变）；目标是把行为压到尽可能像真人 + 出现风控信号即保护性撤退，并对用户诚实、不承诺"绝对安全"。

**保护与可用的平衡（作者指出的反向风险：保护过度 → 授权功能静默死亡）**
> 设计目标不是"最小化风险"，是"**最大化每单位账号风险换来的价值**"。防御机制全是"少花"方向的，必须配平衡机制，否则最安全的行为=永远不用，用户登录了账号却得不到登录才有的价值。
- **预算语义 = 安全额度，不是恐惧上限**：调度器目标是把额度**花完且花在刀刃上**——授权任务按价值排序（目标优先级/内容新旧/是否在追 LEAD），每小时额度分给最值的
- **auth 只干 auth 才能干的事**：匿名路由能拿到等价数据的一律不占授权额度；额度专留给登录墙后的内容 → 账号活动天然集中于不可替代价值
- **AIMD 动态校准**（防"永久保守"的关键）：连续 N 天零风控信号 → 加性小步提速；撞风控 → 乘性砍半+熔断。系统收敛到各平台真实容忍线，"默认保守"只是第一周起点不是终身状态
- **熔断带半开恢复**：冷却结束自动半开——一次低风险探测，成功则阶梯恢复，失败则延长冷却。没有半开的熔断器是功能的无声墓碑
- **低利用率与高风险同等可见**：诊断面板报"本周只用了 30% 安全额度、3 个目标在排队"+ 一键提速；哨兵指标=**授权路由产出占比**，某账号连续一周授权产出为零本身就是告警（过度保护或授权已坏），功能不允许静默失效

**Provider 抽象（愿景 #3）**
- `LLMProvider` 接口：generate + embed 两个能力
- 后端：Gemini（现状）、OpenAI 兼容端点（一个实现覆盖 OpenAI/Ollama/LM Studio/vLLM 等全部本地运行时）、Anthropic
- embedding 优先本地（隐私+免费），无本地则用 provider API，都没有则退化为关键词模式（纯 RSS 模式是永远的地板）

**Token 经济（已有三道闸之上）**
- 结构性省钱：相关性/去重/聚类全在 embedding 层完成，大多数内容从生到死不碰生成模型
- 预算从"每日 token 上限"进化为"每目标每日成本"（token + 浏览器分钟数），UI 可见哪个目标在烧钱

**共享与发布层（OnlyFourBot，愿景 #1 #5 #6 #8）**
- **共享 token 的机制**："先查共享索引，再开火"——本地实例为某话题烧 token 之前，先查询 OnlyFourBot 上是否已有足够新鲜的 digest（按话题/实体 + 时间窗索引）；有则直接拉取（零 token），本地可增量校验；没有则本地生成，并可选推送回共享索引。省的不只是钱，是全网重复算力
- **身份**：Supabase Auth，与作者其他应用共用实例和账号体系（一号通用）；**本地使用永远不需要登录**（隐私原则），登录只在参与共享/发布时需要
- **追溯**：每条共享 digest 携带贡献者账号签名，信源可追溯，垃圾信息可归责
- **信任模型分阶段**：第一阶段只有作者实例 + 受邀者可发布（无需防投毒体系）；开放投稿时再上审核（轻量 AI 分类 + 源域名白名单 + 举报），旧文档里的信誉系统留到那时
- **隐私过滤（发布边界）**：所有内容出本机前过 PII 清洗——地址、身份证/护照号、手机号、邮箱、精确坐标等（扩展现有 services/privacy.py）；授权来源（cookie 抓取）内容**永不出本机**（沿用 security_and_sharing_boundary_plan.md）

**分发与更新安全（愿景 #9）**
- **签名更新是唯一可接受的在线更新方式**：用 Tauri 2 官方 updater 插件——每个更新包用 ed25519 私钥签名，客户端内置公钥，**签名校验不通过直接拒绝安装**（插件强制，无法关闭）。更新清单（latest.json）+ 安装包走 HTTPS 托管在作者域名或 GitHub Releases
- **签名私钥是整个信任链的根**：离线保存（密码管理器），永不进仓库、永不放更新服务器；CI 出包时用 secret 注入。私钥若泄露 = 攻击者可向全部用户推送木马，等级等同数据库主密码
- **平台签名与公证**（独立于 updater 签名，解决系统信任）：macOS 需 Developer ID 签名 + 公证（否则 Gatekeeper 拦截），Windows 可选 Authenticode（EV 证书消除 SmartScreen 警告）
- **更新不需要登录**：更新是安全修复通道，必须对所有用户无条件可达；账号体系与更新通道解耦
- **不做远程代码执行**：应用永不 eval 远程下发的脚本/配置中的代码；共享层下发的只有数据（digest JSON），预设源库更新走带签名的应用更新
- **供应链卫生**：依赖锁定（package-lock / requirements 固定版本）并定期审计；sidecar 二进制打进安装包、被同一个签名覆盖
- **诚实的边界**：无法阻止有人在第三方站点分发改过的安装包——缓解手段是官网/GitHub 为唯一官方渠道 + 发布页公示 SHA256、装机后的更新则由签名机制完全保护

**发布合规策略（愿景 #8 的"摘要还是原文"判断）**
- **发布摘要，永不发布原文全文**。理由：事实本身不受版权保护，受保护的是表达；用自己的话写的摘要 + 指向源头的链接是新闻信件/聚合行业的成熟低风险形态，全文转载则是明确的侵权风险
- 摘要必须带：署名来源 + 原文链接 + 时间戳——网站给源站导流量，既合规又符合"溯源"原则
- 允许**短引用**（关键句，标明出处），不复制付费墙内容，不转存图片（只链接）
- 原文全文只存在于用户本机（个人阅读用途），与公开发布是两个世界
- 网站提供删除通道（takedown），来源方要求即撤
- 本策略与"登录态内容不出本机"叠加构成双重防线

### 3.3 盲区补全（2026-07-05，Claude 洞察，作者愿景之外的八个缺口）

愿景九条集中在"系统如何获取和分发信息"；以下八条在另一侧——"系统如何与人长期相处"。工具活不活看前者，产品成不成看后者。

1. **反馈闭环与告警信任预算**（→R5）：每条告警/线索可标"值得/不值得/别再报(mute)"，负反馈调权（画像向量、来源权重、线索静音）。没有纠错机制的通知产品死于"狼来了"。
2. **合盖问题**（→R1 托盘默认 + R5 唤醒回填）：笔记本睡眠=雷达失明。托盘常驻、系统唤醒后自动回填离线时间窗、共享层补盲区。
3. **冷启动**（→R7，但影响 onboarding 设计）：新用户第一屏直接拉 OnlyFourBot 现成 digest，零 token 零等待先见价值。共享层三重身份：省算力、补盲区、暖冷启动。
4. **自家 AI 的幻觉控制**（→R5）：求真产品被抓到一次 AI 编造即品牌破产。合成优先抽取式；每条结论可勾稽到来源片段（点击对照原文）；AI 生成显式标注；置信不足只给原文关键句+链接、不给结论。
5. **知识状态备份与迁移**（→R4）：一键导出加密迁移包（目标+线索状态+设置），新机导入即恢复。作者本人 Win→Mac 的 DPAPI 之痛就是需求证明。
6. **跨语言同事件归并**（→R3 选型硬性要求）：embedding 模型必须多语言，同一事件的中英文报道归同一线索，否则去重承诺破产。
7. **追赶简报**（→R6）：离开 N 天归来，展示"上次见面状态 → 现在"的 diff（"3 个值得知道的进展"），不是 700 条未读。
8. **省时间可视化**（→R6）："本周过滤 N 条噪音、归并 M 条重复、11 分钟完成 3 小时的摄入"统计面板。用户信任的持续确认 + 作者自媒体演示素材。
